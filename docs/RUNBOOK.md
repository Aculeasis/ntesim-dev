# Build and reproduction runbook

Native source [cancellation and checkpoint/resume](NATIVE_LIFECYCLE.md) use
`run-script --stop-after-inputs N`, `--cancel-file PATH` and `--resume TOKEN.json`.
CLI `--profile NEW_JSON_PATH` and the [native benchmark](NATIVE_PERFORMANCE.md)
measure CPU, peak residency, event/encoding cost and retained transport bytes.

Run commands from the repository root. Python 3.11+, rustup and pinned Rust 1.98.1 are needed for native builds; use the installed Python's absolute path if python is unavailable. Node/npm supplies the browser toolchain. Caches/dependencies live in cache/ and outputs in target/. Ordinary execution requires no installed game.

Multiple targets/profiles grow `target/`. `python tools/cargo.py clean`
removes reusable build artifacts and causes a rebuild; cleanup is deliberate,
not part of ordinary validation. Inactive quality reports and old logs may be
pruned, but preserve active diagnostics, saved evidence, checkpoint receipts
and reusable successes during validation and between checkpoint and commit.
After intentionally removing checkpoint state, regenerate a valid receipt
before committing. Keep the repository `target/` layout: changing
`CARGO_TARGET_DIR` requires a separate migration of runners' fixed paths.

Current machine review outputs live outside Git; authored requests and
independent expected fixtures remain tracked only while current tests consume
them. Native/WASM parity consumes the
current batch input generated by `python tools/check.py -- python
tools/verification_engine.py --prepare-batch-inputs`; generate it before running
`tools/verify_wasm_parity.py`. Missing cache inputs diagnose that prerequisite
instead of falling back to legacy receipts.
Checkpoint runs this cheap producer before parity, even when prior checks are
reused. Preparing inputs is not a domain verification receipt; parity itself
requires completed runs and exact native/WASM reports.

```text
python tools/cargo.py run -p ntesim-cli -- run-script presets/native/live-control.nte
```

This runs one authored seed against live combat state, including loops and

## Agent checkpoints

```sh
python tools/checkpoint.py plan
python tools/checkpoint.py run
python tools/checkpoint.py verify
python tools/checkpoint.py run --fresh --full
python tools/checkpoint.py run --extra-checks cache/checkpoint/extra-checks.json
python tools/checkpoint.py install-hook
```

`plan` prints the changed paths and required commands without running checks. `run` executes or reuses individually fingerprinted successful [boundary checks](DEVELOPMENT.md#choosing-checks) and writes a receipt only when all pass for unchanged inputs. `verify` is silent on success and rejects stale/missing checks or a staged tree different from the tested tree. A failed rerun removes the receipt and preserves the failing exit code; passing earlier checks remain reusable only for unchanged dependencies. `--fresh` clears reuse, `--full` selects all workspace/data/browser boundaries. Finish edits/review before the ordinary run; after a failure use focused checks then rerun once. Add independent task checks as a JSON array of argument arrays, for example `[["python", "tools/cargo.py", "test", "-p", "ntesim-content", "mint", "--locked", "--offline"]]`; the runner resolves `python` to its own interpreter and executes without shell expansion. Source checks remain silent on success with full logs under `cache/tool-logs/`.

Native mechanics work uses Rust/native checks. Source/report/WASM changes add bounded WASM/Worker smoke checks; web/JS edits and run --full retain full native/WASM/Worker parity and browser checks. [Check selection](DEVELOPMENT.md#choosing-checks) owns exact paths and reuse semantics.

`run` also saves per-command elapsed seconds and exit codes to `cache/checkpoint/timings.json`, including completed checks in a failed batch and `reused: true` for cache hits. Input mutation reports changed paths and retains only independently unchanged successes, but never issues a receipt. This diagnostic file does not authorize a commit; only the unchanged-input receipt does. Compare warm runs separately from first builds after changing compiler profiles, and avoid concurrent measurements when comparing elapsed times.

## Native checks

```sh
python tools/cargo.py test --workspace --locked --offline
python tools/cargo.py fmt --all -- --check
python tools/cargo.py clippy --workspace --all-targets --locked --offline -- -D warnings
python tools/cargo.py clippy --workspace --all-targets --locked --offline -- -D warnings
python tools/check.py -- python -m unittest discover -s tests
python tools/check.py -- python tools/python_tests.py
python tools/cargo.py build -p ntesim-cli --locked --offline
```

Offline requires the exact compiler and cached dependencies. Remove --offline only when an approved dependency/toolchain download is needed. The helper enforces the pin and local cache/output policy.

Checkpoint runs standard Rust formatting and Clippy alongside existing architecture checks. Java/PMD tools and quality baselines are retired. Use standalone checks for focused debugging; checkpoint selects them before delivery.

Ordinary checks are silent on success. Cargo/web runners and `tools/check.py` save complete stdout/stderr in `cache/tool-logs/`; errors print bounded diagnostics with a log path and retain the failing exit code (including 2). Use `--verbose` only when debugging:

```sh
python tools/cargo.py test --verbose -p ntesim-core --locked --offline
node tools/web.mjs test --verbose
python tools/check.py --verbose -- python -m unittest discover -s tests -p test_cargo.py -v
python tools/cargo.py test -p ntesim-content mint --locked --offline
```

Wrap other finite tests, verifiers, generators and acquisition commands with `tools/check.py`. Prefer focused checks after a batch; read targeted failure-log sections instead of dumping full reports. `cargo run`/metadata and interactive web dev preserve their normal output contracts. `check.py` is for exit-code-based checks, not for piping machine-readable reports to another program.

`tools/python_tests.py` runs all Python test files in isolated processes, at most four at once on the inherited four-CPU affinity. Use `--pattern test_agent_checkpoint.py` for a focused file; failure output and exit codes are preserved. Kit verifiers write current run outputs under `cache/`; `--refresh-receipt` can retain a cache copy under `cache/reviews/`.
## Current CLI examples

`target/debug/ntesim.exe inspect-script presets/studio/s1.nte` returns the entire ordered party, canonical equipment IDs, exact compiled static stats and initial resources without running the rotation. `compile-script` returns that party alongside an executable live source artifact or source diagnostics; `validate-script` returns diagnostics only. [Script API](../openspec/specs/script-inspection/reference.md) defines null/zero, coordinate and failure semantics.

On Windows use target/debug/ntesim.exe; other hosts use target/debug/ntesim.

Native source workflows require no scenario JSON. `run-script SOURCE.nte`
retains the executed source, exact build/scenario request, source occurrences,
native causal trace, model assumptions and replayable report. `batch-script
SOURCE.nte examples/native-source-experiment.json` runs the explicit distinct
seeds with fresh lexical/combat/RNG state. `compare-scripts BASE.nte CANDIDATE.nte
examples/native-source-experiment.json` pairs those seeds, checks common dummy,
stop, incoming, initial-party-resource and critical-policy assumptions, and
returns exact candidate-minus-baseline damage and real-duration DPS deltas.
Signed fractions use decimal strings; means require every requested run to
qualify. Unknown model assumptions, failed admissions, event/work limits and
failed victory horizons retain their receipts and never contribute a mean.
The combined comparison event/receipt budget covers both arms. An experiment
cannot start another trial without reserving its per-run event allowance.
Seed variation is sampling within the declared model, not model uncertainty.

`export-script SOURCE.nte NEW_OUTPUT_DIR` runs the authored seed and saves
`report.json`, `manifest.json` and eight CSV tables: damage packets, grouped
contributions, state timeline, healing, energy, input-time intervals, builds and
assumptions. The destination must not exist. Source input is bounded to 4 MiB;
the report JSON must fit the 64 MiB replay limit. File hashes in the manifest bind
the generated artifacts. CSV rows retain source/request hashes and seed; exact
amounts use decimal integer terms, with nested typed receipts/state in quoted
JSON cells. Preserve those integer terms when importing into tools with limited
numeric precision. `report.json` retains the complete executed source, builds,
scenario, stop policy, limits, identities, assumptions, occurrences, failures and
native receipts. Later source edits or moving the report do not change it.

`replay-script OUTPUT_DIR/report.json` rejects changed identities or report views,
then compares the full source rerun and the full native replay. Its exit 0 means
the saved outcome reconciled, including an expected failed/incomplete prefix;
`success` and `execution_completed` retain the actual saved combat outcome.
`export-script` writes such partial reports but exits 2; compilation failures
return typed diagnostics without creating the output directory. Partial damage
stays visible without successful DPS or comparison eligibility. Timelines are
event-boundary observations, not resumable combat checkpoints. For example:

```text
python tools/cargo.py run -p ntesim-cli -- export-script examples/mint-native-cycles-r1.nte target/mint-report
python tools/cargo.py run -p ntesim-cli -- replay-script target/mint-report/report.json
```

`search-scripts examples/native-source-search.json` evaluates the authored R1/R5
Mind Royale variants over the same two continuing Mint periods and explicit seeds.
Candidate `source` paths are relative to the search-request file; each file is
ordinary editable/shareable `.nte`, including its `add stats` and equipment.
The public request selects `mean_damage` or `mean_dps`, `maximize` or `minimize`,
and 1..=64 candidates. Ties retain authored order. Only candidates with every
requested seed eligible enter `ranking`; a rejected candidate does not erase a
valid candidate's score. Partial rankings explicitly describe only the evaluated
eligible subset. No global or exhaustive build-optimum claim is made.

`max_new_trials` (1..=64000) stops at a completed trial boundary. Save the report's
`checkpoint` object as UTF-8 JSON and pass it to `search-scripts REQUEST.json
CHECKPOINT.json`. Only `max_new_trials` may change while resuming the same inputs.
Source bytes, candidate order/IDs, objective, seeds, compiled builds, engine and
cumulative budgets are bound to the checkpoint; file relocation is permitted.
The checkpoint retains actual completed/failed trial receipts and validates their
hash, ordered seed prefix and cumulative work/size accounting. It is a trial
boundary, not a mid-combat scheduler checkpoint. Exhausted immutable event or
receipt budgets cannot be expanded by resuming. `complete` means all search
trials were evaluated; `success` additionally requires every candidate to qualify.
The command exits 2 for a paused, budget-stopped or rejected-candidate report.

```sh
target/debug/ntesim build-stats examples/build-stats.json
target/debug/ntesim studio-build-catalog
target/debug/ntesim run-game examples/game-scenario.json
target/debug/ntesim batch-game examples/research-crit.json examples/research-game-batch.json
target/debug/ntesim compositions
target/debug/ntesim acceptance-spec
```

These commands consume current typed content and maintained research inputs; some compile partial static inputs or execute incomplete research models. compositions enumerates teams; it does not search executable optimal rotations. pilot, search-builds, acceptance-run and validate-finalist are research scaffolding; successful output cannot satisfy strict acceptance. Their optional inputs are request JSON/checkpoints, not an arbitrary output directory. Full current syntax is in crates/cli/src/commands/ and each task-specific contract.

## Browser and WASM

```sh
node tools/web.mjs install
python tools/cargo.py build -p ntesim-wasm --release --target wasm32-unknown-unknown --locked --offline
node tools/web.mjs check
python tools/check.py -- node tools/build_studio_scenarios.mjs
node tools/web.mjs format-check
node tools/web.mjs test
node tools/web.mjs dev
```

install uses the committed lockfile under cache/web. The studio generators require a current native CLI: stats use the audited frozen catalog; scenarios execute the active examples before generating browser inputs. Historical review receipts are not active templates. test rebuilds production assets when the selection includes offline tests. dev serves localhost:5173 and does not register a Service Worker.

Install the pinned binding generator once: `python tools/cargo.py install wasm-bindgen-cli --version 0.2.128 --locked --root cache/wasm-bindgen --jobs 4`. The Cargo helper generates version-matched glue and declarations in `target/wasm-bindgen/` after every successful WASM build. The studio and Node tests load `target/wasm-bindgen/ntesim_wasm_bg.wasm`; raw Cargo WASM is only a generator input. Rebuild after Rust changes. Vite bundles the processed binary and generated glue into `target/web/assets/`. Shared authored transport sources live in `crates/wasm/js/`; generated files remain untracked.

Measure full S5 batches in an isolated Node Worker with `python tools/cpu_limit.py -- node tools/benchmark_wasm_transport.mjs`. Seven alternating warm measurements compare binary with lossless JSON on the same engine, seeds and full reports; `	arget/verification/wasm-transport.json` records medians, byte sizes, artifact identities and exact equality. This transport benchmark does not establish gameplay coverage or browser UI throughput.

Focused tests accept repository-relative `web/tests/...` or web-relative `tests/...` paths; omitted paths run the full suite. Node test flags use `--flag=value` syntax. The runner uses four file workers, a 120-second deadline per file and a 180-second overall deadline (`NTESIM_TEST_TIMEOUT_MS` overrides the latter). Full logs and individual test durations remain in `cache/tool-logs/`.

The WASM URL-loading test uses an in-process Fetch transport with real `Request`, `Response`, body streams and WASM compilation in both the main thread and the actual Worker. It checks request origin/method/path, streaming versus byte fallback, MIME parameters, HTTP 404 and corrupt bytes without requiring a TCP permission prompt. Set `NTESIM_TEST_LOOPBACK=1` to exercise the same assertions through a real local HTTP server on a host permitting loopback. Ordinary checkpoints use the deterministic transport; no game engine or Worker behavior is mocked.

```sh
node tools/web.mjs test web/tests/wasm_contract.test.mjs
node tools/web.mjs test web/tests/streaming_trials.test.mjs
```

Build current native/WASM artifacts before boundary tests. The source contract smoke test compares CLI and WASM compilation and checks structured diagnostics and error propagation. Worker streaming and replay tests exercise the presentation consumers. Character, weapon and combat arithmetic assertions live exclusively in Rust under `crates/content/src/simulation/tests/`; the duplicate JavaScript mechanics suite has been removed.

`python tools/cargo.py run -p ntesim-cli -- compile-script presets/native/live-control.nte` returns the native live-program response. `validate-script SOURCE.nte` returns structured source diagnostics and exits 2 when diagnostics are present. Compilation retains exact source, work limits, identities and the initial scenario without unrolling live loops. Save the whole UTF-8 JSON response and use `run-compiled-script FILE.json` to execute it through the same live runner as `run-script SOURCE.nte`.

The CLI `run-game-suite SCENARIOS.json` accepts an array of 1–512 independent game requests (16 MiB maximum). It returns ordered `reports`, shared current-content/request identities and the hash of the complete request array. Failed execution receipts remain visible and produce exit 2; scenario validation errors include their array index. `project-studio-actors REQUESTS.json` similarly projects 1–512 actor requests (4 MiB maximum) with one current-content projection. Single-request commands retain their contracts.

Web commands automatically bundle the authored [studio scripts](../presets/studio/README.md) and their catalog. Edit `presets/studio/*.nte` and `index.json`; no manual generator or TypeScript edits are needed to add a menu preset. Development watches these inputs. Native request fixtures remain separate.

```sh
python tools/cargo.py build -p ntesim-wasm --release --target wasm32-unknown-unknown --locked --offline
python tools/check.py -- python tools/verify_wasm_parity.py --output target/verification/wasm-parity.json
```

Follow [WASM parity](../openspec/specs/wasm-transport/reference.md) for synchronizing the engine artifact after Rust changes and [web architecture](WEB_ARCHITECTURE.md) for production/offline details. Serve target/web. Reload after a new production cache activates; cache version is derived from built content, not an old numbered checkpoint.

CLI execution returns exit 0 only for completed requested work, exit 2 for a preserved incomplete/failed result, and exit 1 for request/engine or report-output errors. Successful report output is pretty JSON followed by a newline. A closed or unwritable stdout returns exit 1 without a panic; diagnostics are best effort if stderr is also unavailable. Content `quality=incomplete` is separate from execution completion. A budget-limited `pilot`/`acceptance-run` prints its JSON report to stdout with `checkpoint.is_complete=false` and exits 2. Capture that output, extract the `checkpoint` object into a separate JSON file, and pass that file as `CHECKPOINT.json` when resuming; the CLI does not accept the whole report as the checkpoint. For example, in PowerShell:

```powershell
$reportPath = 'target/pilot-report.json'
$checkpointPath = 'target/pilot-checkpoint.json'
New-Item -ItemType Directory -Force target | Out-Null
& target/debug/ntesim.exe pilot examples/pilot.json | Out-File -FilePath $reportPath -Encoding utf8
$pilotExit = $LASTEXITCODE
if ($pilotExit -ne 2) { throw "Expected incomplete exit 2, got $pilotExit" }
python -c "import json,pathlib; r=json.loads(pathlib.Path('$reportPath').read_text(encoding='utf-8-sig')); pathlib.Path('$checkpointPath').write_text(json.dumps(r['checkpoint']), encoding='utf-8')"
& target/debug/ntesim.exe pilot examples/pilot.json $checkpointPath | Out-File -FilePath target/pilot-resumed-report.json -Encoding utf8
$resumeExit = $LASTEXITCODE
if ($resumeExit -notin @(0, 2)) { throw "Unexpected resume exit $resumeExit" }
```

Use the same capture/extract pattern for `acceptance-run`, substituting its request path and command arguments. On exit 2, inspect the report and retain its checkpoint. A budget-limited prefix can resume; `pilot` also returns 2 when all units were processed but `failed_units` is nonempty, and resuming that same request preserves those failures. `verify-tabular` returns exit 0 only when every case has an exact/within-tolerance status. Documented discrepancies are separate from `failed_cases` but still produce exit 2; see [tabular status semantics](../openspec/specs/calibration/reference.md#status-and-report-interpretation).

## Reproduction and release

Build and verify a host-native CLI archive with all 23 source recipes and native
dependency licenses using the [native distribution workflow](NATIVE_DISTRIBUTION.md).
It uses the pinned toolchain/lockfile and excludes browser artwork and research
data packages. Publication remains separately authorized.

Build and verify a static Studio archive through the
[browser distribution workflow](BROWSER_DISTRIBUTION.md). It retains exact
runtime notices and SVG visuals, excludes game artwork and exercises the
relocated application in Chrome. No deployment or publication is implicit.

Save exact engine/data/input identities, seeds, hypotheses, budgets, reports and commands. Use independent verifiers appropriate to the mechanic; existing reviews are historical evidence, not checks rerun for a new commit. Benchmarks are optional measured workloads, not gameplay validation.

Release checks follow the [release contract](../openspec/specs/distribution/reference.md), [baseline](../openspec/specs/product-scope/reference.md#first-usable-baseline) and [modeling policy](DEVELOPMENT.md). The repository's current v0.1.0 metadata does not mean that acceptance or publication is complete.
