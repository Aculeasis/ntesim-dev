# Research build-to-run binding

This research service connects audited static builds to partial execution. Complete native build/kit/rotation coverage remains pending; generated reports do not establish validated game DPS.

`run-game-built REQUEST.json` takes the combined request in `examples/built-game-research.json`. It requires schema 1, scenario mode `research`, an explicit `hypothesis`, projection policy `known_static_additive_v1` and exactly one equipment build per actor slot. The CLI audits the frozen package and binds the combined request bytes, all 17 build tables, four metadata files and engine identity. Input is limited to 4 MiB. The in-memory core receives tables/coverage and performs no file access.

Each build combines character/weapon progression, authored console stat additions and declared 2-/4-piece set effects. Canonical character/weapon/set IDs, character level and weapon tier must agree with the scenario. Only characters marked released in coverage are admitted; this does not establish release status for weapon/set candidates. All actor slots must be unique and matched. Initial maximum HP must equal the compiled HP, and current HP cannot exceed it. Unknown IDs, invalid stat additions/set counts and missing builds fail before execution.

The projection replaces every manual static field from exact string fraction receipts: character plus weapon base ATK, derived ATK/HP/DEF, CRIT rate and additional CRIT damage. It never reconstructs these values from display floats. Fractions are reduced and checked for overflow. Base ATK, HP and DEF must be integral. Derived HP and DEF are computed from the complete exact additive pool, then quantized once to nearest integer with exact halves upward under the bounded `build.stat_quantization_v1` runtime policy shared with Studio. The native game rule remains unverified and stays in the [quantization dossier](quantization.md); no damage, healing or shield rounding is inferred from this policy. Missing receipts are errors, never zero defaults.

Projected field `hp_percent` records the complete static percentage pool and receipts preserve the contribution breakdown; projection must not apply a producer twice. Owner-specific awakening HP rules are in [Edgar's card](../characters/edgar/action-damage.md); the shared selection boundary is [selection integration](../../../reviews/q10-game-action-binding/awakening-selections.md).

The compiler also replaces manual ChargeEfficiency procs with the exact native `ChargeGetEfficiencyBase` multiplier, including unconditional equipment additions. A unit multiplier needs no proc; duplicate manual efficiency procs and invalid multipliers fail. Actor build receipts retain the native attribute and replaced procs. Implemented numeric grants use the recipient multiplier and fractional carry; explicit pool fills retain their existing policy.

Native projection preserves `damage_bonus` from `DamageUpGeneralBase` and `elemental_bonuses` for all six native elements: CHAOS, COSMOS, INCANTATION, LAKSHANA, NATURE (Anima) and PSYCHE. Delivery selects the bonus using the packet's resolved element, including delayed/off-field packets. General and matching-element bonuses add in the damage zone; physical/mental packets retain the general bonus and true damage bypasses that zone. Unknown element keys and invalid ratios fail before combat. Native `DamageUpPsychicallyBase` projects into `mental_damage_bonus`, distinct from Psyche, for eligible Mental packets. Nonzero `DamageUpNormalBase` typed build bonuses remain unsupported.

The legacy research field `elemental_bonus` remains an additional actor-element-only scalar for existing structured fixtures; native projectors emit zero there. It is not a general bonus. Hit receipts expose `static_general_damage_bonus` and `static_element_damage_bonus` (including that legacy scalar when it matches), before damage-kind policy and temporary modifiers. These fields describe selected stat inputs, not the final bonus zone; true damage ignores both. Separate identities are retained in compiled builds, script requests and exports. `node tools/web.mjs verify_damage_bonuses.mjs` independently checks native Mint damage, six off-field elements and full CLI/WASM/Worker report parity, writing current receipts under `target/verification/damage-bonuses/`.

Action coefficients, timings, energy capacity, initial energy, proc eligibility/amounts and awakenings remain the caller's partial scenario. Build compilation does not validate those inputs against native action/passive graphs. Every actor receipt includes the replaced manual stats, compiled stats, native element mapping and full build report with contribution/evidence/unresolved fields. The output includes `compiled_scenario` for explicit downstream research batch input and `execution` for the bounded run. Compilation never mutates the caller request.

Top-level status remains `INCOMPLETE`; quality is `incomplete`, and strict/DPS/acceptance flags remain false even when execution completes. CLI exit 0 means an output report was generated; invalid compilation exits 1. Check `execution.success` and `execution.execution_completed` separately. Strict mode rejects the projection hypothesis. Existing `run-game` remains a caller-supplied partial scenario path.

The optional [native action-coordinate projection](native-action-projection.md) separately replaces caller ATK rates from selected source receipts under an additional hypothesis. Without it, action coefficients remain caller inputs. Actor slots and character identities are both unique.

Compiled scenarios now carry `model_assumptions`, a map of stable IDs to visible descriptions. Static/action/gear projection hypotheses are attached automatically; Mint skill projection also attaches its purchase-coordinate and resonance rules. Conflicting caller descriptions for a compiler-owned ID fail rather than overwrite provenance. Caller assumptions are retained. The runner exports the same map, and native seed/timing batches retain it at the aggregate boundary and in failed partial reports. These descriptions are metadata, never proof of support or permission to compute complete game results.

The map is optional and omitted when empty. At most 32 custom entries are allowed; exact canonical ID/description pairs from the finite engine hypothesis registry do not consume that allowance. A mismatched canonical description counts as custom and still fails if its hypothesis is reached. Every entry requires 1..128 ASCII identity characters (letters, digits, `_:-./`) and a nonempty description of at most 4096 UTF-8 bytes. Strict requests require canonical matching entries. Browser contracts/import/export preserve the map, results expose it in execution details, and the trial collector rejects a report whose assumptions differ from the declared request before aggregation. Original and exported scenario/engine hashes bind the metadata alongside the other inputs. The native/WASM/Worker tests and `tools/verify_built_skill_levels.py` check preservation; readiness flags retain their existing semantics.

Verification uses independent Rust stat/threshold checks and native/WASM/Worker replay. Console geometry and allocation are outside the model; see [equipped builds](equipment-builds.md).
