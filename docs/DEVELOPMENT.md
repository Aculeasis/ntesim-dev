# Development guide

[OpenSpec](../openspec/README.md) owns accepted behavior and selected changes. [Runbook](RUNBOOK.md) owns executable commands; architecture and mechanics references retain implementation rationale and evidence. Code and current checks establish executable capability.

## OpenSpec workflow

Use Node.js >=22.12.0 and Python 3.11+. Install the repository-pinned CLI into the ignored cache:

```powershell
python tools/openspec.py setup
python tools/openspec.py --version
python tools/openspec.py list
python tools/openspec.py view
```

`view` is OpenSpec's terminal dashboard of specs, changes and task completion. It is not a product-readiness percentage or gameplay certification. No separate implementation queue, research counter or completion ledger is maintained.

The six tracked Codex skills in `.agents/skills/` are generated by OpenSpec 1.16.1. They call `openspec` on PATH. For Codex sessions use the same pinned installation:

```powershell
npm.cmd install --global --ignore-scripts --no-audit --no-fund @fission-ai/openspec@1.16.1
openspec --version
```

The global install writes outside the checkout and may require approval. If installation or protected `.agents/` writes are blocked, report the actual restriction and request permission; do not silently omit integration. Fresh checkouts retain generated skills and require no regeneration. Change the pin and regenerate skills together for an upgrade. The project wrapper disables telemetry by default and caps validation concurrency at four; it does not silently download dependencies during checks.

Agents run the CLI examples inside generated skills through `python tools/openspec.py`, retaining the original arguments. This enforces the pin and four-CPU process limit without modifying upstream skills. The plain global command remains available for discovery and manual invocation.

1. Select the user's requested change, or resume the saved selected change. With several open changes and no selection, ask which one; with none, await a real request instead of inventing a backlog.
2. Explore only the relevant capability, detailed reference, mechanics evidence and current implementation. Draft a focused proposal, behavioral delta, design and verifiable tasks using the standard `spec-driven` schema. `$openspec-propose` is planning-only; use `$openspec-apply-change` when implementation is authorized. A user request to perform the full work already supplies that authorization.
3. Implement the tasks and keep their checkboxes and artifacts current. Update a requirement's complete block and scenarios under `MODIFIED`; keep supporting reference edits in the same change. Pure refactors/tooling/docs without behavioral changes can declare `skip_specs: true` in `.openspec.yaml`. Do not manufacture requirements for a typo or implementation-only edit.
4. Run the applicable existing tests and review the diff. `python tools/openspec.py validate --all --strict --no-interactive --concurrency 4` checks documents; `python tools/checkpoint.py run` checks the affected integration boundary. Requirements are not proof of passing tests or verified game facts.
5. After tracked tasks and checks pass, synchronize and archive. The generated archive skill offers interactive sync choices. For an explicitly authorized complete CLI lifecycle, `python tools/openspec.py archive CHANGE --yes` validates, applies deltas and archives locally without a second confirmation. Avoid archive overrides that bypass validation or skip required spec sync. Then run `python tools/openspec.py validate --archived --strict --no-interactive --concurrency 4` and checkpoint on the final tree before committing.

Use short behavior requirements with concrete GIVEN/WHEN/THEN scenarios. Keep public formats/limits in a capability's detailed reference, decisions in design/ADRs and source facts/uncertainty/independent calculations in mechanics references. Delete obsolete documents and repair links. Archived OpenSpec changes preserve actual work; do not import pre-migration completion prose as fictional changes.

## Evidence and modeling

Record source facts, reasoned model hypotheses, applicability limits and independent numerical or causal checks separately. Checkable sources and defensible models need no extra approval. An unresolved reached damage dependency prevents complete success; a deliberately omitted DPS-irrelevant detail needs an explicit causal rationale. Synthetic tests validate a model, not native game facts. Current compatible evidence can supersede an old finding without building historical patch migration infrastructure.

## Adding a mechanic

1. Identify its owner, scenario closure and direct/indirect DPS relevance under the [scope policy](../openspec/specs/product-scope/reference.md#dps-relevance-and-modeling-boundary). Reuse cheap full behavior; record scoped simplifications/omissions of costly irrelevant detail. Review applicable constants, combat descriptions and references. For uncertain rules, choose a defensible explicit model hypothesis with rationale/checks; retain unsupported branches.
2. Bind typed values/units/conditions and explicit model assumptions in data or the reviewed content contract. Keep source receipts and frozen bytes; research overrides remain explicit.
   Reuse the domain's existing receipt and adapter table when only owner IDs or constants differ. Ordinary hit energy uses `OrdinaryHitEnergyBasis` and `hit_basis`; add owners to the energy table and independent cases to `simulation/tests/ordinary_hit_energy.rs`, not new owner-specific basis types or copied suites. Receipts use only `hit_basis`; obsolete owner-specific input fields are rejected.
   Native weapon projection uses the adapter table in `build/gear.rs` for both native compilation and Studio, and the shared compile, unit-conversion and receipt helpers in `build/weapon_projection.rs`. Add owner projection and validation under `weapons/<owner>/` or `sets/<owner>/`; `gear/validation.rs` routes proc variants but owns no item IDs or item-specific constraints. Keep character primary-packet routing in `registry/`.
   Research constructors resolve admitted primary packets through that registry; historical preview effects can be child packets and cannot define executable input identity. Bind research critical eligibility to the admitted effects. Integration examples must acknowledge reached hypotheses and either finish scheduled effects or explicitly expect a horizon cutoff; test unsupported outcomes separately from successful execution.
3. Add shared reusable behavior to core, character/weapon/set transitions to their owner in content, and orchestration to research. Do not add source-site brands or another preview default.
4. Connect admission, packet delivery, callbacks, resources/clocks and final receipts in the actual gameplay path. A synthetic service alone does not complete the mechanic.
5. Check formula values against independent calculations or compatible damage spreadsheets; verify causal logic, invalid inputs and native replay. Keep assumptions/unsupported branches visible. Update the owning card and commit the tested result under the [delivery rules](../AGENTS.md#checks-and-delivery). Use the affected-boundary checks below.

## Test scope

Before adding a test, inspect existing coverage and identify the meaningful behavior or failure it would detect that current checks miss. A change does not automatically need a new test; extend an appropriate existing check when possible. Mechanics and independent numeric expectations belong to their Rust domain owner. CLI checks cover argument/file handling, diagnostics, output and the distinct risks of native build binding, aggregation and replay; adding a character alone does not require another CLI mechanics suite.

Repeat a check across layers only for a distinct integration risk. Combine inputs that exercise the same behavior without hiding different causal paths or failure modes. Prefer small shared fixtures over copied setup, but do not build a new test framework just to shorten tests. During cleanup, remove confirmed duplicates and preserve unique checks; moving a test between crates alone does not remove duplication.

There are no test-count, test-LOC or code-to-test ratio targets, quotas or checkpoint requirements. Use these measurements only for a requested audit. A lower line count is not sufficient reason to remove a test.

## Toolchain

Python 3.11+ and rustup on PATH are required by tools/cargo.py. It verifies pinned Rust 1.98.1, looks in local and installed toolchains, and in online mode can install the pin into local cache. Offline/frozen mode fails without the compiler/dependencies; it does not download. Cargo.lock pins Rust dependencies.

Node/npm and the committed web lockfile feed tools/web.mjs; dependencies/caches stay in cache/, outputs in target/. Native-only mechanic checks do not require Node or a WASM build. API smoke checks and web work use that retained toolchain. Ordinary checks require no installed game, acquisition root or reference checkout.

Network configuration comes from the caller's environment. Under managed Codex
networking, Cargo inherits the supplied `HTTPS_PROXY` unless `CARGO_HTTP_PROXY`
was explicitly set. No endpoint or credentials are configured by the repository.

`tools/cargo.py`, `tools/check.py` and `tools/web.mjs test` restrict checks and their children to at most four logical CPUs on Windows/Linux. Environment defaults for Cargo build jobs, Rust test threads and Rayon/OpenMP pools are capped at four; smaller environment limits are preserved. Explicit thread/job flags still run within the same CPU affinity. Web tests use at most four workers, including when a higher concurrency flag is supplied. Run standalone checks through `tools/check.py` to inherit the CPU limit. This process-local setting does not change system configuration.

Only the GitHub Pages deployment build sets `NTESIM_BUILD_CPUS=all` together with
`GITHUB_ACTIONS=true`. In that explicit context, the shared limiter preserves the
runner's available affinity and does not impose pool defaults; caller-provided
limits survive in nested Cargo, staging and Team list processes. Either variable
alone leaves the local cap enabled. Local validators still share four CPUs and
run one at a time; the deployment job runs build preparation without validators.

The dev profile optimizes `serde_json` and `sha2` at level 2 and the package-audit owners `ntesim-data` and `ntesim-cli` at level 1. The test profile inherits these settings, allowing tests and the native CLI oracles to reuse dependency artifacts. Debug assertions and integer overflow checks remain enabled; other workspace crates keep their normal debug optimization level. Release/WASM settings, test scenarios and evidence validation remain unchanged. The first build after changing profiles recompiles affected artifacts; subsequent checks reuse them.

Verification scripts use `tools/verification_workspace.py` for unique directories under `cache/`. Ordinary `mkdir` retains inherited Windows sandbox ACLs; Python 3.13 `tempfile.TemporaryDirectory` uses mode 0700 and can remove that access. The helper confines creation and cleanup to the workspace cache and changes no existing ACL. Kit oracles write current run outputs under `cache/`; `--refresh-receipt` can retain a cache copy under `cache/reviews/`. Generated verification output is not a tracked development input. WASM parity output defaults to `cache/verification/wasm-parity.json`.

The Cargo helper fingerprints manifests, lock/toolchain, runtime Rust sources and bundled research inputs with sorted paths and length-prefixed bytes. Separate test modules do not alter runtime identity; checkpoint test receipts still bind test sources and fixtures. A direct Cargo build without this environment fingerprint reports it unavailable. Do not claim an old engine identity for changed sources.

## Local configuration

### Studio build identity

The header links to the public repository and the build's source. Ordinary local
builds and development-server sessions identify checked-out HEAD: main shows its
short hash, another branch shows `branch/hash`, and detached checkouts show only
the hash even when a local tag points there. Dirty builds retain that HEAD label;
it identifies the last committed base, while engine/input fingerprints still bind
the actual simulator sources. Only validated explicit deployment tags replace
the hash. Ref links use the commit tree or the exact tag namespace.

The Studio shows the build-start UTC instant embedded in the loaded WASM. It
uses the Vite build's instant from `build-info.json` while WASM is unavailable.
Browser release preparation passes a shared instant to both builds. Each viewer
sees `dd.mm.yy · hh:mm` in their current time zone, including daylight-saving and
date boundaries. Reloads retain the served build's instant. The semantic `time`
element retains UTC.
See [browser distribution](BROWSER_DISTRIBUTION.md) for deployment preparation.

### Machine-specific settings

The optional ignored `.local/` directory owns machine-specific configuration.
Agents read `.local/AGENTS.md` as a supplement to the shared root guide when it
exists. Keep only local differences there. Shared setup and checks require no
local supplement, installed game, private proxy or API credentials.

Keep private permission rules under `.local/` or in the agent's user configuration.
If a sandbox prevents a documented command, obtain a narrowly scoped local grant
for that machine; do not commit its absolute paths or another user's approval.
The normal formatter entry point is `node tools/web.mjs format`.

### Studio Team list generation

Studio preset definitions are maintained in `presets/studio/index.json` and its
referenced `.nte` script files. The derived browser bundle
`web/src/generated/script-presets.json` is a disposable artifact ignored by Git;
supported Studio build, development and web validation commands prepare it
automatically from maintained sources whenever it is absent or stale. Editing
presets requires updating only the manifest or `.nte` files; regenerating the
bundle leaves the Git worktree free of generated preset changes.

The selectable scripts in `presets/studio/index.json` also populate Team list.
The preset bundle is synchronized automatically before Team catalog validation.
The team display projection and mean DPS in `web/src/generated/team-list.json`
are computed ahead of time by the shared Rust engine through the current WASM
trial-session API:

```powershell
python tools/cargo.py build -p ntesim-wasm --release --target wasm32-unknown-unknown --locked --offline
python tools/check.py -- node tools/web.mjs teams
python tools/check.py -- node tools/web.mjs teams-check
python tools/check.py -- node tools/web.mjs build
```

Refresh explicitly when a new DPS calculation is wanted. Local source edits,
WASM rebuilds, ordinary builds and routine checks retain the last calculation;
they neither recalculate DPS nor reject a catalog solely for differing source
identities. Structure and exact source loading remain checked. An explicit
refresh requires current WASM and records its real engine/source/generator
identities. Matching requested calculations may reuse `cache/studio-teams/`;
changed calculation inputs cannot reuse an old result. Format the generator
before explicit refresh. No previous calculation cache is required.

For explicit release preparation, build with `python tools/browser_distribution.py build
--release --output target/ntesim-browser-release.zip --offline`. This explicit
release preparation builds current WASM and runs `teams --fresh` for every
delivered selectable script before packaging. Failed or incomplete new results
remain unavailable. An ordinary local distribution build omits `--release` and
does not recalculate the catalog. GitHub Pages deployment uses this ordinary build
and ships the committed Team list without recalculating DPS. Packaging does not authorize publication.

Generation processes one scenario at a time under the four-CPU wrapper and
reuses matching results in `cache/studio-teams/`. Add `--fresh` to the `teams`
command to calculate every entry without reading that cache. Raw calculation
outcomes remain in `cache/`; only deterministic display fields are bundled.
The mean comes directly from Rust, with the script's authored iterations, seed
sequence, crit mode, targets and stop/duration conditions. Twenty complete curated
teams share 1,000 iterations, 120 relative seconds and the documented
[comparison profile](../presets/studio/teams.md), including fifteen useful console
substat lines per character. S5 remains the unchanged default control under its
own historical build and target conditions. Older partial examples are retained
outside selection for regression coverage. The list retains conditions and native
assumptions in generated metadata; ranking is each authored scenario's DPS.
Failed or incomplete
calculations remain loadable with unavailable DPS and a reason.

Pass external paths and secrets through environment variables. For a reusable
local file, create `.local/.env` with plain `KEY=VALUE` lines and run:

```powershell
python tools/check.py --env-file .local/.env -- python tools/python_tests.py
```

Set any required local settings in that file. Ordinary builds and checks do not
require private environment variables. There are no implicit installation paths.

`--env-file` loads only the explicitly named file. Blank lines and whole-line
`#` comments are ignored; values may have matching single or double quotes.
Values are literal: no shell execution, interpolation, escape processing,
multiline values, `export` statements or inline comments. Inherited environment
variables take precedence. Do not include real values in examples or logs.
`.env` files, `.local/` and `.venv/` are ignored; `.venv/` is a Python environment,
not a configuration file. No current build requires an API key.

Checkpoint checks commit-eligible inputs for private configuration, machine paths,
proxy endpoint literals and recognizable credentials. Forced tracked local files
also fail. Diagnostics report locations/categories, never matched values. These
checks are a regression boundary, not a guarantee against every kind of personal
data; preserve required public third-party attribution and review the diff.

## Opt-in throughput measurements

Primary Damage is the checked integer sum of each settled hit's existing
half-up rounded damage. It includes overkill; applied HP loss is separately
capped by remaining target HP. Two hits of 100.4 count as 200 Damage, two hits
of 100.5 count as 202, and a 100 hit against 30 HP counts as 100 Damage,
30 HP loss and 70 overkill. Team, actor, source, target and time-bin summaries
use this same basis. DPS divides that total by the selected positive elapsed
duration and can remain fractional. Detailed hit diagnostics retain the raw
exact formula values; JSON preserves exact wide integer totals as `N/1` and
contribution CSV emits their decimal integer. There is no statistics-mode toggle.

`tools/throughput.py` measures the prepared live source executor and the Rust
Studio collector. It is an explicit development experiment, outside checkpoint
and Team list calculation. Run from any working directory using the checkout's
script path; relative source/output arguments resolve against that checkout.
Outputs must stay in `cache/`; Cargo outputs stay in `target/`.

```powershell
python tools/throughput.py native --build --output cache/exact-throughput/native --count 1000 --repetitions 3
python tools/throughput.py wasm --build --output cache/exact-throughput/wasm --count 1000 --repetitions 3
python tools/throughput.py chunks --output cache/exact-throughput/chunks-4 --workers 4 --count 1000 --repetitions 3
python tools/throughput.py workers --output cache/exact-throughput/pool-4 --workers 4 --count 1000 --repetitions 3
```

`chunks` uses one, two or four compute Workers plus a dedicated aggregator,
identical chunk APIs and explicit per-instance warmup. `workers` uses the actual
Studio controller and interprets `--workers` as total pool size; its parallel
path reserves one for aggregation. A two-Worker production pool therefore has
one compute Worker. The single-Worker production path uses the session API.
Keep these distinct when comparing scaling. All processes/threads share the
normal four-logical-CPU cap; run only one measurement or validator at a time.

Native `--diagnostics --build` enables phase/count and allocation measurements
through a non-default development feature. Compare headline timings without
that flag. `--oracle` separately retains detailed per-seed mechanics hashes and
independent sums of rounded hit receipts; its detailed execution/serialization
cost is outside the throughput comparison. Ordinary CLI/WASM/Studio builds do
not select the benchmark target or diagnostics feature.

For alternating historical/current measurements, retain the release benchmark
binary and complete `wasm-bindgen/` directory under `cache/`, with a manifest
containing `engine_source_sha256`, `damage_total_policy`, and a `files` object
mapping archive-relative paths to SHA256. Pass its path with `--reference`.
The driver verifies every archived file, binds the manifest hash, and checks
the executed engine identity. This development-only boundary cannot build or
select diagnostics/profiling artifacts; current application import contracts
are unchanged. Preserve old receipts and create new output directories for
reruns rather than changing the historical policy labels.

`--profile profiling --build` inherits release optimization, thin LTO, one
codegen unit and abort behavior while retaining symbols. Native outputs go to
`target/profiling/`; WASM and glue go to
`target/wasm32-unknown-unknown/profiling/` and
`target/wasm-bindgen-profiling/`. Ordinary generated glue is separate. The
profiling WASM preserves debug information through the same available optimizer.

Portable release measurements use level 3 and ThinLTO. Native PGO is a local
experiment with the pinned `llvm-tools-preview` component. Build the
`ntesim-throughput` target in separate target directories with the encoded
Rust flags `-C profile-generate=<absolute training directory>` and
`-C profile-use=<absolute merged profile>`, respectively. Use the same source
snapshot and release settings for both builds. Train the first executable
with the benchmark inputs and merge its `.profraw` files using the pinned
`llvm-profdata merge -o <merged profile> <raw profiles>`. Record the flags,
input identities, profile hashes and uninstrumented output identity. Pass
encoded flags only to the individual build process. The pinned
`wasm32-unknown-unknown` target lacks `profiler_builtins` for PGO.

Receipts bind runtime/source/artifact/tool identities, versions, affinity,
requested work, raw repetitions, process CPU, peak residency and timing
boundaries. Raw results retain observations/samples and aggregates. Report
execution, collection, first sample, initialization, transport/decoding and
aggregation separately, with median and spread. Process resource totals also
include raw receipt output; native observation-oracle work is untimed explicitly.
An incomplete or stale run leaves a failed receipt. See
[browser performance](BROWSER_PERFORMANCE.md) for production browser measurements.

`chunks --chunk-size 25|50|100` selects a fixed chunk size for the matched
compute experiment. `--shared-aggregator` reuses one compute Worker for the
final collector pass. This harness measures compute occupancy and collector
cost separately. The production controller commits observations during execution.

The native benchmark and source Worker share the typed batch outcome and Studio
collector. Compact execution validates hit parentage, the input-time partition,
elapsed clock totals and energy reconciliation while aggregating observations.
The first report and explicit replay sample retain detailed frames. Failed
batch seeds are executed again for a detailed diagnostic. Compare the compact
and detailed observations with `--oracle` on the native benchmark and use raw
receipt performance phases only within the corresponding detail level.

## Choosing checks

Run the focused existing owner/crate/transport check while implementing. Finish edits and review before `python tools/checkpoint.py run`; checkpoint selects formatting, Clippy, affected native tests, tooling and document checks and reuses valid successes. Fix failures with focused checks, then rerun the stable-tree checkpoint. Source/report/adapter changes select current native/WASM builds and bounded `wasm-smoke`; web and JavaScript tooling changes retain full Worker/replay/aggregation and native/WASM transport checks. Ordinary native mechanics changes do not force a WASM build or DPS refresh.

Maintained `presets/research/` CSV/conditions changes select affected Rust consumers, native/WASM rebuilds and minimal Worker smoke without the full browser suite. Crate-local CSV fixtures select their owning existing tests. Check fingerprints include these inputs; Cargo identities include maintained bundled research inputs. A changed CSV must not reuse a stale test success or old bundled artifact.

Core mechanics and independent numeric/causal expectations belong in Rust. Remove duplicate tests and obsolete verifiers; consolidate related cases in existing boundaries. Keep distinct transport, replay, package and UI checks where those risks exist. Local Team list validation is structural and never performs full DPS recalculation. Explicit refresh and release preparation own calculation freshness.

The baseline validates privacy, Markdown links/anchors and JSON/TOML syntax. OpenSpec changes run strict active and archived validation. Tooling changes run isolated Python files sharing four logical CPUs. Quality uses `python tools/cargo.py fmt --all -- --check` and `python tools/cargo.py clippy --workspace --all-targets --locked --offline -- -D warnings`; Java/PMD and quality baselines are retired.

Use `python tools/checkpoint.py run --wasm-smoke` at native integration milestones. `run --full` is for explicit complete integration/distribution acceptance. Production browser lifecycle/performance uses `node tools/web.mjs verify-trials --browser`; see [browser performance](BROWSER_PERFORMANCE.md). Ordinary checkpoints do not prepare a release or recalculate Team list DPS.

Successful checks and builds are cached individually under `cache/checkpoint/successes.json`, binding dependency bytes, modes, commands, environment, executables and consumed artifacts. Rust package tests track individual upstream dependency closures, skipping unchanged passing packages when downstream crates or unrelated tests are edited. Builds (`native-build`, `wasm-build`) reuse previous successes when their dependency closures and binary artifacts are unchanged. Failures are never cached. Static and privacy checks run fresh; unknown checks are uncached. A receipt binds the complete unchanged worktree and HEAD; partial staging or edits during checks fail. `run --fresh` forces selected checks to run again. Never edit receipts/cache records to claim success. Read `cache/checkpoint/timings.json` for scope, elapsed times and reuse markers, separating build costs from test execution.

Checkpoint uses stable `TEMP`/`TMP` under `cache/tmp` and Windows `LOCALAPPDATA` under `cache/checkpoint/localappdata` in execution and environment keys. All validators and children share at most four logical CPUs; run one validator at a time. Ordinary success is silent; failures identify bounded diagnostics and full logs under `cache/tool-logs/`. Use `--verbose` for debugging.

Add a genuinely independent check with `run --extra-checks cache/checkpoint/extra-checks.json`, an array of literal argument arrays executed without a shell. Reuse existing owner checks; do not add a verifier framework or copied suites. CLI exit 0 means the operation succeeded, not that incomplete research became strict gameplay acceptance.

New acquisition uses explicit roots/permissions. Only reviewed repository tools run; no game code or untrusted downloaded scripts. Runtime and ordinary tests need no installed game or historical raw package. [Runbook](RUNBOOK.md) owns concrete commands.
