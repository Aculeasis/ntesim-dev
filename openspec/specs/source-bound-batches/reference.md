# Source-bound research batches

Detailed interface and model reference for this [capability](spec.md). Requirements and scenarios live in that spec; this reference retains formats, bounds and technical rationale.

Q10d3 connects [build binding](../../../docs/mechanics/shared/native-build-projection.md) and optional [native action-coordinate binding](../../../docs/mechanics/shared/native-action-projection.md) directly to [budgeted research batches](../research-batches/reference.md).

`batch-game-built BUILD_REQUEST.json BATCH.json` compiles the combined build request once, without running a pilot scenario, then passes the compiled scenario to the existing seeded/timing batch runner. The build request is limited to 4 MiB and batch request to 1 MiB. Existing batch seed, timing, event, retention and all-or-none statistics rules apply unchanged. Compile/action-count failures and invalid batch preflight fail without a report. Failed or truncated experiments return the preserved binding and partial batch receipts with statistics withheld.

The top-level receipt retains the complete `build_binding`, including every actor/action source receipt and explicit hypothesis, and the nested `batch`. It binds original build bytes (`request_sha256` and `build_request_sha256`), original batch bytes (`batch_request_sha256`), audited metadata/tables (21 hashes, or 25 with action projection) and engine identity. `input_sha256` is SHA-256 over UTF-8 `ntesim-built-game-batch-v1` followed by each original input's 8-byte big-endian length and exact bytes, build first then batch. This distinguishes different source requests even when their replaced manual stats compile to identical scenarios.

`compiled_scenario_sha256` binds the UTF-8 compact JSON of `build_binding.compiled_scenario`, with object keys in lexical order, no extra whitespace and unescaped Unicode. The nested batch's `scenario_sha256` matches it. The existing per-run seeded identities and batch identity remain intact. No hidden preview run consumes RNG, events or trial budget. Build compilation/audit and shared provenance metadata are outside the batch's retained per-run byte budget; that budget is not a peak-memory or total-output bound.

`complete` means every requested partial experiment trial completed. Status/quality remain `INCOMPLETE`/`incomplete`, with false strict/DPS/acceptance flags. Exit 0 means the requested experiment completed; exit 2 means an incomplete experiment report is available; exit 1 means compilation/preflight failed. No strict game, finalist, sustainable-cycle or performance acceptance gate is advanced.

Rust integration checks source/input hashes, equality with direct batch runs, absence of an extra execution, equivalent compiled scenarios from different original inputs and failed-run statistics suppression. `tools/verify_built_game_batch.py` reconstructs Mint static stats and three selected action coefficients from original hash-checked exports, then verifies 1000 seeds across three timing conditions (3000 runs), exact totals/means and sample variance, canonical provenance hashes, replay, two rejected preflight requests and two incomplete failure/budget cases. The pilot request bytes and verification receipt are in `reviews/q10-built-batch/`. Timing conditions use this sparse partial fixture; they do not establish native timing sensitivity or actual game DPS.
